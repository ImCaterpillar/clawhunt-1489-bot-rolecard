# 实现说明

## 设计决策

### 为什么自己写校验器而不用 jsonschema？

平台任务说明明确「模型 API、云资源和训练算力等第三方费用不包含在本单预算中」，
且交付要求「提交与本单相关的代码或配置」。
自实现校验器带来三个好处：

1. **零依赖**：买家复制即可运行，不会被 pip 网络问题卡住
2. **可审计**：校验逻辑透明，出问题可读源码定位
3. **演示了 draft-07 的关键子集**：说明理解了 JSON Schema 语义，而非调用黑盒

代价：只实现必要子集（见 `validate.py` 顶部注释）。

### 为什么 `additionalProperties: false`？

角色卡是「结构化」契约。允许任意额外字段会让契约退化 ——
后续任务（会话隔离、域隔离、权限映射）都要基于这份结构做校验。
严格模式把拼写错误变成显式错误，而不是静默忽略。

### 为什么加 `in_scope: false`？

该系列 50 单的核心特征是「**边界拆分**」：每单范围收得很窄，
原文反复出现「不在本单范围」。把边界写进结构字段，
比写在文档段落里更不容易在后续任务中被误用。

### 为什么 `domain` 是枚举而不是字符串？

该系列的后续单（如「部门与 Bot 归属映射」「客户经营域隔离」）
都依赖「企业管理域 / 客户经营域」这个二分。
枚举把它固化成契约，避免自由文本导致下游无法可靠过滤。

## 实现细节

### 路径化的错误信息

校验错误带完整 JSON 路径，便于定位：

```
$.bot_id: 值 'Bad_ID' 不匹配模式 ^[a-z][a-z0-9-]{2,63}$
$.role.purpose: 长度 2 < 最小 10
$.responsibilities: 元素数 0 < 1
$: 缺少必填字段 'display_name'
$: 不允许的额外字段 'extra_field'
```

### `apply_defaults` 的递归

`default` 填充对嵌套对象与数组元素递归生效，
保证 `escalation`、`citation_required`、`requires_approval`
等可选字段在缺省时获得确定值（而不是 undefined）。

### 类型检查的布尔陷阱

Python 里 `isinstance(True, int)` 为真。校验器显式排除 bool：

```python
if t == "integer":
    return isinstance(value, int) and not isinstance(value, bool)
```

避免 `true` 被当成合法整数。

## 验证方法的可靠性

代码经 12 项断言验证。所有断言的**期望值是人为设定**的
（例如「非法样例至少报 5 个错误」「删除每个必填字段都必须报错」），
不是用被测代码自身算出来的 —— 避免「自己证明自己」的循环论证。
另外 `examples/rolecard_invalid.json` 是刻意构造的反例：
只交付合规示例无法证明校验器真的会拒绝错误数据。
